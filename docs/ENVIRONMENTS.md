# 本稼働と次期バージョン(2つの世界)

ログインしたあと、**本稼働**と**次期バージョン**のどちらで遊ぶかを選べる。正式リリースすると、次期バージョンが本稼働になる。

| | 本稼働(live) | 次期バージョン(next) |
|---|---|---|
| 入口 | `/live/`(従来の `/` の画面も、ここにつながる) | `/next/` |
| コード | 最後にリリースした版(タグ) | `main` の最新 |
| データ | 保存され続ける | **消えてよい**(リリースのたびに消す) |
| アカウント | 持ち主(登録・停止・パスワード) | 本稼働のものを**読み取り専用**で使う |
| 同時接続 | 100人 | 30人 |

- ポータル(`/`)でログイン・新規登録をして、世界を選ぶ。ゲーム画面のメニューの「🌐 世界を選ぶ」で、いつでも選び直せる。
- **同じ名前・パスワードで、どちらの世界にも入れる。** 会社のデータ(資金・路線・施設)・会社名・プロフィール・色・最後に見ていた場所は、世界ごとに別。
- 新規登録は本稼働側で行われる(次期バージョンのアドレスで登録しても、本稼働側に作られる)。利用停止(BAN)も本稼働側が持ち主で、両方の世界に効く。
- 次期バージョンは、本稼働のデータを**読み取り専用**で見るだけ(compose の `:ro` の mount)。次期バージョンで何をしても、本稼働のデータは壊れない。

## 構成

```
ブラウザ ──→ web(入口: nginx) ──┬─ /      ポータル
                                ├─ /live/ 本稼働のクライアント ──→ server        (本稼働のコード / multi-data)
                                └─ /next/ 次期のクライアント   ──→ server-next   (main のコード / next-data)
                                                                      └─ multi-data を読み取り専用で mount(アカウント)
```
- 本稼働のクライアントは、本稼働のコードから作る(`LIVE_SRC`)。次期バージョンのクライアントは、このリポジトリから作る。版が違っても、通信の仕様が食い違わない。
- ポータル(`portal/`)は、版に依存しない静的な画面。

## 日々の運用

**次期バージョンを更新する**(`main` に PR が取り込まれたあと)
```
git switch main && git pull
scripts/up.sh next          # 次期バージョンだけ作り直す(次期のデータは残す)
scripts/reset-next.sh       # 次期のデータを消して、新しい世界で起動し直したいとき
```

**正式リリースする**(次期バージョンを本稼働にする)
```
scripts/release.sh v0.2.0
```
1. `main` にタグ `v0.2.0` を付けて push する(`main` が最新・変更なしであること)
2. 本稼働のデータを `backups/` にバックアップする
3. 本稼働のコードをそのタグに切り替え、本稼働を作り直す(**本稼働のデータとアカウントは引き継ぐ**)
4. 次期バージョンのデータを消して、新しい世界で起動し直す(次の版の準備)

> 保存データの形が変わる版では、本稼働の世界を作り直す必要が出ることがある。その場合は、リリースの前に決めておく(バックアップは `backups/` に残る)。

**本稼働だけ作り直す**(緊急の修正を、リリースの版として出すとき) … 修正を `main` に取り込み → `scripts/release.sh v0.2.1`

## 初めて切り替えるとき(従来の1つだけの構成から)
```
git tag v0.1.0 <今の本稼働と同じコミット>   # 例: この機能を取り込む直前の main
git push origin v0.1.0
scripts/live-checkout.sh v0.1.0             # 隣のフォルダ(../rivalines-live)に、本稼働のコードを取り出す
scripts/up.sh                               # 入口・本稼働・次期バージョンを起動(本稼働のデータは、今の volume をそのまま使う)
```
本稼働の volume は、従来と同じ名前(`multi-data`)のまま使うので、データもアカウントもそのまま続く。

## 1つのコードだけで試す(初めて動かすとき)
本稼働と次期バージョンで版を分けず、同じコードで両方を起動できる。
```
LIVE_SRC=. docker compose up -d --build
```

## 設定(環境変数)
- `LIVE_SRC` … 本稼働のコードを置いたフォルダ(既定 `../rivalines-live`)
- `PROJECT` … compose のプロジェクト名(既定 `simulator-multi`。試験用に別の名前で、別の世界を立てられる)
- `GATEWAY_PORT` … 公開するポート(既定 8092)
- サーバー側: `ENV_NAME`(live / next)・`ENV_LABEL`(画面の表示名)・`APP_VERSION`・`ACCOUNTS_FROM`(アカウントを借りる先のフォルダ。指定すると読み取り専用になる)

## 注意
- `/api/admin`(運営用)は、入口からは届かない(`docker compose exec` で使う)。次期バージョンの停止・削除は、本稼働側で行う。
- 本稼働のサーバーが止まっていると、次期バージョンでも新規登録・ログインはできない(アカウントの持ち主が本稼働のため)。すでにログイン済みの人は、そのまま遊べる。
